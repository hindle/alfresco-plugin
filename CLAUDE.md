# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview
This Wordpress plugin is deployed on a Wordpress site running a custom theme built using Elementor. The plugin covers automations based on Trello card transitions and timings as well as custom fucntionality for the website it is deployed on.

## Repository layout

This repo contains a single WordPress plugin, **Alfresco Learning**, in `alfresco-learning/`. It powers a specific site: outdoor education workshop bookings, a membership-gated "Planning Hub" of downloadable teaching resources, and CPD content — with Outseta for membership/auth and Trello as the operational backend for the workshop booking pipeline. The repo root only holds packaging/deployment scripts (`build.sh`, `dev-sync.sh`) and local scratch files (`.env`, `requests.http`) — there is no root-level `package.json` or `composer.json`; all plugin code and tooling lives under `alfresco-learning/`.

## Commands

All JS/build commands run from `alfresco-learning/` (that's where `package.json` lives):

- `npm install` — install JS deps
- `npm run build` — compile Gutenberg blocks (`blocks/*`) with `wp-scripts build`, output to `alfresco-learning/build/`
- `npm run start` — `wp-scripts start`, watch mode for block development
- `npm run lint:js` / `npm run lint:css` — lint blocks with `wp-scripts lint-js` / `lint-style`
- `npm run format` — `wp-scripts format`

PHP deps use Composer with a **classmap** autoloader (not PSR-4), scoped to `includes/`:

- `composer install -d alfresco-learning`
- `composer dumpautoload -d alfresco-learning` — needed after adding/removing/renaming a class file under `includes/`, since the classmap is generated by a directory scan rather than resolved by namespace convention at runtime

There is no automated test suite (no PHPUnit, no JS test runner). The closest thing to one is `requests.http` at the repo root — a gitignored, developer-machine scratchpad of manual REST calls (including live Trello calls) used to exercise the `alfresco/v1` routes and Trello webhooks by hand.

### Packaging / deployment

`./build.sh` (repo root) runs the full release pipeline: `npm run build` → PHPCS/PHPCBF via `~/projects/PHP_CodeSniffer` (an **external sibling checkout, not part of this repo** — this step only works on machines that have it) → `composer dumpautoload` → assembles a clean copy of the plugin into `./build/alfresco-learning/` → zips it to `alfresco-learning.zip`. This copy step is also what nests the compiled block output into `includes/build/`, which is where the plugin's PHP actually expects it (see Gutenberg blocks gotcha below).

`./dev-sync.sh` mirrors `alfresco-learning/` into a local DevKinsta WordPress install — hardcoded to `~/DevKinsta/public/alfrescolearning/wp-content/plugins/alfresco-learning/`, this developer's machine only.

## Architecture

### Bootstrap

`alfresco-learning.php` is the plugin entry point: it loads the Composer autoloader and instantiates `Alfresco\Alfresco` (`includes/Alfresco.php`). That one constructor wires up everything — WP header cleanup, custom post type/taxonomy registration, AJAX/REST endpoint registration (delegated to `AJAX.php`), third-party `<script>` injection (Outseta, MailerLite, Google Analytics) on `wp_head`, script enqueueing, an onboarding-page login gate, and Gutenberg block registration. There's no router/framework beyond this — new functionality is generally added as a private method wired into that constructor, or as an addition to `AJAX.php`.

### HTTP entry points (`AJAX.php`)

`includes/AJAX.php` is the single hub for both legacy WordPress AJAX actions (`wp_ajax_*` / `wp_ajax_nopriv_*`) and the plugin's REST routes (`register_rest_route` under the `alfresco/v1` namespace). Almost every route uses `permission_callback => '__return_true'` (unauthenticated by design — the only manual auth check is the download endpoint's Outseta cookie); match that convention for new routes unless there's a specific reason not to. Each route decodes the JSON request body and hands it to a handler class in `Enquiry\` or `Workshop\`.

Handler classes share an informal contract: constructed with the raw decoded-JSON `stdClass` body, exposing `validateData()` and `saveData()`. `Workshop\*` classes (`GFOL`, `Space`, `Castles`, `Seaside` — the four workshop types) extend the abstract `Workshop\Workshop` base class for shared fields and Trello card creation. `Enquiry\*` classes (`Training`, `Invoice`, `Payments`, `Feedback`) implement the same `validateData()`/`saveData()` shape independently rather than sharing a base class.

### Trello as the workshop booking pipeline

The workshop booking process is modeled as a Trello board: cards move between lists as a booking progresses (new enquiry → payment policy sent → booking confirmed → invoiced → welcome-email window → weather check → feedback → follow-up). All list IDs and card custom-field IDs are literals in `Trello\Constants`. `Trello\Client` wraps the Trello REST API with Guzzle; `Trello\WorkshopCard` hydrates a typed value object from a card's custom fields.

Transitions are triggered two ways:
- **Card moves** — `Trello\WebhookHandler::workshopBoard()` (hit via the `/trello-workshop-webhook` REST route) reacts to Trello's card-move webhook and fires the relevant transactional email (cancellation policy / booking confirmation).
- **Time-based** — `Trello\WorkshopActions` (welcome / weather-check / feedback / follow-up / policy-reminder emails) is meant to be invoked periodically; each has its own public REST GET endpoint (`/send-*-emails`) intended to be hit by an external cron rather than WP-Cron. The feedback email body comes from `templates/email-feedback.html` via `file_get_contents()` + `str_replace()` placeholder substitution, not a WP template function.

`Trello\Client` reads `TRELLO_API_KEY`/`TRELLO_API_TOKEN` via `parse_ini_file()` from a `.env` five directories above `includes/Trello/`. When the plugin is deployed inside a real WordPress install, that path resolves to the **site root** (sibling of `wp-content/`) — not this repository's own root `.env`.

### Outseta-gated downloads

`PHDownload` (`includes/AlfrescoPHDownload.php` — "PH" = Planning Hub throughout this codebase, see also `js/phUnit.js` and the `al-ph-unit` script handle) validates an Outseta RS256 JWT (public cert embedded in source) via `firebase/php-jwt`, checks the account's subscription stage against the Outseta CRM API, then returns a 10-minute presigned S3 URL (bucket `alfresco-downloads`) for the requested PDF. AWS credentials load from a hardcoded production filesystem path (`/www/alfrescolearning_623/deployment/.aws/...`), so that lookup only succeeds on the production server.

### Gutenberg blocks

Blocks live in `blocks/<name>/` (`block.json` + `index.js` + `editor.scss`/`style.scss`), built with `@wordpress/scripts` into `alfresco-learning/build/<name>/`, and registered server-side in `Alfresco::registerBlocks()` via `register_block_type()`.

**Gotcha**: `registerBlocks()` reads from `includes/build/<name>/`, but a plain `npm run build` writes to `alfresco-learning/build/<name>/` — those only end up in the same place after `build.sh`'s copy step. A block edited and rebuilt locally won't appear in WordPress until either `build.sh` runs or `alfresco-learning/build/` is manually copied into `includes/build/`.

### Custom post types & taxonomies

Registered in `Alfresco::registerCustomPostTypes()`: `al_planning_unit` (Planning Hub content, slug `hub-unit`) and `al_cpd_unit` (CPD Units, slug `cpd-unit`), with taxonomies `year-group`, `subject`, and `planning-category`.
